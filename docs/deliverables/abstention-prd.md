### 1.1 双维度归因表：7 类 GAP_KINDS × X 码

### 1.4 关键机制发现：多道 guard 级联拦截（放大弃权）

**这是根因分析最重要的结构发现**。`judge.py:_all_blockers()`（`:367-412`）显示弃权被**多道 guard 依次串行拦截**，且存在「依赖查询未执行」的短路：

```json
{
  "guard_cascade": [
    {"order": 1, "guard": "source_parse",   "code": "X6", "line": 374, "trigger": "parse_status != 'parsed'"},
    {"order": 2, "guard": "binding",        "code": "X3", "line": 375, "trigger": "binding_status in {unknown,unresolved,disagreed,pending}"},
    {"order": 3, "guard": "source_scope",   "code": "X3", "line": "source_semantics", "trigger": "_source_scope_issue()"},
    {"order": 4, "guard": "definition",     "code": "X3", "line": "unresolved_source_definition_issue"},
    {"order": 5, "guard": "source_binding", "code": "X3", "line": "source_binding_issue()"},
    {"order": 6, "guard": "metric_spec",    "code": "X2", "line": 389, "trigger": "account in METRIC_SPECS and spec is None"},
    {"order": 7, "guard": "fact_lookup",    "code": "X3", "line": 395-397, "trigger": "任一前置 guard 失败 → lookup_status='not_executed'"}
  ],
  "short_circuit_rule": "line 395: (source_failures or parse_status!='parsed' or abstention_code in {X3,X6} or binding_status异常) → 直接 add('X3','fact_lookup','依赖事实查询未执行') 并 return"
}
```

**产品影响**：`ABSTENTION_SMALL_SAMPLE.md` 明确——「**130 个已解析条目在调用绑定模型前被来源前置校验阻断，另有 25 个条目尚未完成解析**」。即：一旦前置 guard 拦截，事实查询根本**不执行**，就算材料里其实有可核对数据也无法证明。这是「账本处理完成但金融召回未达标」的直接机制原因。

同样，`verify.py` 中 X3/X6 有 **20+ 处分散触发点**（`:754,777,801,818,821,836,839,897,932,940,946,954,962,985,991,993,1222,1242,1348`），说明定义缺口不是单点问题，而是贯穿全链路的系统性缺口。

## 2. 产品定义

### 2.1 Product Goals（3 个正交目标）

1. **提升「有效核实率」而非降低弃权率**——把可判定的弃权转为 verified/violated，同时**保证 verified 精确率不降**（红线：不得引入造假风险）。
2. **让弃权「可行动、可补齐」**——把 313 条弃权从「黑箱放弃」变成用户可据以补材料/声明定义的结构化缺口清单（`build_gaps()` 已具备雏形）。
3. **建立产品价值度量**——用「有效核实率 + 缺口可闭环率」替代当前只有技术收据的现状。

### 2.2 User Stories

| # | As a... | I want... | So that... |
| --- | --- | --- | --- |
| U1 | 金融分析师 | 上传研报后能知道**哪些数字被核对了、哪些没有** | 不把「几乎全弃权」误读为「报告有问题」 |
| U2 | 金融分析师 | 对每条弃权看到**缺什么、补什么材料能救回** | 一次补齐材料而非盲目重跑 |
| U3 | 合规/风控 | verified 的每条都有宿主内核产生的金额证据 | 信任结论，规避造假风险 |
| U4 | 产品运营 | 看到「有效核实率」趋势与缺口分布 | 判断产品是否真的在变好 |
| U5 | 用户 | 对「券商自定义指标」这类可澄清口径，能**显式声明**后重跑 | 把 X3 定义缺口转为可核实 |

### 2.3 验收标准（可度量）

| 指标 | 现状 | 目标（阶段一） | 目标（阶段二） |
| --- | ---: | ---: | ---: |
| 有效核实率（verified+violated / 全部候选） | ~1.9%（6/319） | ≥15% | ≥35% |
| verified 精确率（盲标抽检） | 未知 | ≥98% | ≥98% |
| 弃权可闭环率（缺口有补齐路径） | 低 | ≥80% | ≥95% |
| 事实查询执行率（未被前置 guard 短路） | ~59%（130/219被阻断） | ≥85% | ≥95% |

> 「事实查询执行率」来自 `ABSTENTION_SMALL_SAMPLE.md`：130/220 已解析条目被前置阻断。
